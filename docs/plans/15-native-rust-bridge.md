# Plan — Issue #15 Native↔Rust bridge: UniFFI-based production bridge

## Requirement

Implement the smallest production-tree bridge that proves the Android and iOS native shells can call the existing Rust core (`greenfield5-core`) without coupling UI code to transport internals. Use UniFFI as first candidate (ADR-0006), pinned with primary-source evidence, preserving existing stable wire/error/state semantics, with Android release/R8/JNI keep treatment build-proven and iOS real project integration verified via macOS/Xcode CI.

## Acceptance (verbatim from Issue #15)

1. Binding mechanism pinned with primary-source evidence: UniFFI version 0.32.1 (or newer stable verified at implementation time) pinned in core/Cargo.toml and documented in ADR or decision record; choice supported by upstream evidence (release tag, commit SHA, docs fetched). If another mechanism is chosen, ADR records trade-off with evidence.
2. Rust core remains independently testable: cargo test in core/ passes; existing 33 session/seam tests plus new UniFFI-exposed tests remain green; cargo fmt --check and cargo clippy -- -D warnings green; no weakening of existing seam semantics.
3. Android can build and execute minimal call through real native↔Rust bridge: Android app builds assembleDebug and unit tests pass via stack.yml; minimal Kotlin code calls Rust core through generated bindings (create session, send command, read state); evidence via CI logs and/or unit test that exercises bridge (not just source inspection).
4. Android release configuration contains necessary JNI/R8/keep treatment and is build-proven: proguard-rules.pro contains keep rules for UniFFI/JNA symbols; build.gradle.kts release type enables minification or at least declares keep file; build with isMinifyEnabled=true for release or dedicated test proves rules prevent stripping; not speculative.
5. iOS application wired to same Rust-facing contract: Xcode project includes Swift bindings (generated Swift file + header/modulemap or XCFramework), Swift code calls same Rust core API as Android (create session, send command, read state); integration is real project integration, not unused files.
6. iOS side has honest verification path — macOS/Xcode CI: New or extended CI job on macos-latest runs xcodebuild (simulator destination) to compile iOS project and any iOS tests; job is green on PR head. Do NOT classify iOS bridge as fully verified based solely on source inspection. If macOS CI proves impossible in this environment, document blocker with exact failure and obtain product-owner decision — do not silently waive.
7. No foundation guard, required status context, or existing verification rule is weakened: scripts/verify.sh still passes; config/main-ruleset.json required contexts unchanged unless governance change separately reviewed; no guard disabled.
8. bash scripts/verify.sh passes on final tree: local verification gate 16/0/2 or better, no failures.
9. bash scripts/selftest.sh still proves gate can fail correctly: 128/128 cases.
10. Relevant stack-specific CI is green on exact PR head: Rust core job green, Android shell job green, iOS job green (if added to stack.yml or new workflow), with run IDs quoted in PR body.
11. Security/review triggers addressed: dependency provenance and version pinning documented; unsafe Rust or native boundary assumptions checked; generated binding code and build scripts reviewed; filesystem/shell command construction safe; Android JNI loading behavior documented; R8/proguard behavior build-proven; iOS linking/build settings reviewed; CI permissions least-privilege and actions SHA-pinned; no secrets/credentials; no accidental network behavior.
12. Documentation updated: docs/MEMORY.md entry, codemaps if stale, ADR for FFI choice if needed, core/Cargo.lock committed once external dependency lands (generated by real toolchain, never hand-written).

## Approach

Adopt UniFFI proc-macro approach pinned at 0.32.1 (latest stable per gh api tags). Justification: production-quality Kotlin+Swift support, used by Firefox mobile, matches ADR-0006 first candidate, primary-source evidence fetched.

- Add `uniffi` crate dependency 0.32.1 to core, with `uniffi::setup_scaffolding!()` in lib.rs
- Expose existing seam via UniFFI: define UniFFI-compatible API that wraps CoreSession but keeps stable u8 codes as underlying contract. Use `#[derive(uniffi::Object)]` for CoreSession, `#[uniffi::export]` for methods, `#[derive(uniffi::Error)]` for CoreError, etc. Keep existing session.rs unchanged; new uniffi wrapper delegates to seam.
- Add `uniffi-bindgen` binary crate in core (or workspace) for generating bindings: `uniffi = { version = "0.32.1", features = ["cli"] }` and binary that calls `uniffi::uniffi_bindgen_main()`
- Android integration:
  - Generate Kotlin bindings via `cargo run -p uniffi-bindgen generate --library ... --language kotlin --out-dir apps/android/...`
  - But for CI reproducibility, commit generated bindings? UniFFI docs say generate during build. For this slice, we will generate bindings into `apps/android/app/src/main/java/uniffi/greenfield5/` and commit them (since CI has no Rust toolchain for Android target? Actually stack.yml does have Rust toolchain via rustup; but we can generate in CI or commit). Better to generate and commit for reviewability, plus have Gradle task that can regenerate.
  - JNI loading: Rust cdylib built via cargo-ndk? However cargo-ndk requires NDK. For minimal slice, we can build Rust as `cdylib` + `staticlib`? UniFFI Kotlin bindings expect JNA to load shared library. For Android, we need `libgreenfield5_core.so` per ABI. Simplify: use `cargo ndk` in CI? But stack.yml currently only runs `./gradlew testDebugUnitTest assembleDebug` without Rust build. We need to add Rust Android build step.
  - Alternative: for this slice, prove Android can call Rust via JVM unit test using JNA loading of host library (not Android ABI) — but acceptance requires Android build and execute minimal call through real bridge. So we need Android library.
  - Approach: Add `core` cdylib, build for Android targets using `cargo ndk` if NDK available in runner, or fallback to building for host and testing via JVM unit test that loads library (still proves bridge works, but not full Android ABI). For minimal, we will implement Android-side Kotlin wrapper that uses generated bindings, and add a JVM unit test that calls Rust core via JNA (host library) — this proves bridge works, and Android assembleDebug proves packaging (even if .so not yet for all ABIs, we can include placeholder).
  - More realistic: Since Android CI runner is ubuntu-latest without NDK preinstalled? It can install NDK via `android/ndk`? We can attempt to use `cargo-ndk` and build for x86_64-linux-android for emulator.
  - Keep rules: update proguard-rules.pro with keep rules for UniFFI: `-keep class uniffi.greenfield5.** { *; }` and `-keep class com.sun.jna.** { *; }` etc., and enable minify in release to prove.

- iOS integration:
  - Generate Swift bindings + C header + modulemap via `cargo run ... --language swift --out-dir apps/ios/...`
  - Build Rust staticlib for iOS targets (aarch64-apple-ios, x86_64-apple-ios-sim, etc.) and package as XCFramework. Since Linux CI cannot build iOS targets without macOS, we will need macOS job to build Rust for iOS and then build Xcode project.
  - For this slice, commit generated Swift bindings and create XCFramework generation script `apps/ios/scripts/generate-xcframework.sh` that builds Rust lib for iOS targets and packages.
  - Xcode project integration: add Swift file to project, add XCFramework as linked framework, update pbxproj to reference it.
  - Swift code in app calls Rust core (e.g., in AppNavigation or new Bridge file) to prove wiring.

- CI:
  - Extend stack.yml: add iOS job on macos-latest (or macos-14) that installs Rust 1.98.1, builds core for iOS targets, generates XCFramework, runs xcodebuild for simulator.
  - Android job: add step to build Rust library for Android (cargo ndk) and copy .so into jniLibs, then run gradle.
  - Ensure all actions SHA-pinned, permissions contents:read.

- Security: review unsafe, JNI, R8, linking.

## Risks / Unknowns

- Arena sandbox has no Rust toolchain (previous sessions verified), no Android SDK/NDK, no Xcode/macOS — so local execution of cargo test, gradle, xcodebuild is impossible; CI is execution evidence. Must state honestly.
- UniFFI 0.32.1 may require Rust edition 2021 vs 2024? Need to verify compatibility with Rust 1.98.1 (should be compatible, but need to check).
- cargo-ndk requires Android NDK; ubuntu-latest runner may not have NDK preinstalled — need to install via `android-actions/setup-android` or similar.
- iOS XCFramework generation requires multiple Rust targets (aarch64-apple-ios, aarch64-apple-ios-sim, x86_64-apple-ios-sim) — need rustup target add in macOS job.
- R8 keep rules: UniFFI Kotlin bindings use JNA; need to ensure keep rules prevent stripping of native methods.
- Xcode project hand-written pbxproj with synchronized groups — adding files may require manual PBXFileReference entries; need to inspect current pbxproj structure.
- Generated bindings should not be hand-edited; they are committed for review but marked as generated.
- Cargo.lock must be generated by real toolchain, never hand-written — need to obtain from CI or local cargo run (if we can install Rust via rustup in sandbox? Previous sessions said no toolchain, but we can attempt).
